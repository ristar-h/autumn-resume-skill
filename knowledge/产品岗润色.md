# 实习/工作经验/项目经历

解读用户的实习经验

## 结构

如果是实习/工作经历，在每段经历的标题处，看用户是否写清楚：公司名称、职位、时间段。 如果是项目经历，标题写清楚该项目名称以及时间

以项目制填写。比如写「XX 功能」，下面另起一行用 list 写：

- 功能/项目的背景
- 用户在其中的职责（视情况另起几行写）

## 内容优化表述

做产品最关注：这个功能的场景到底解决了什么问题。

产品同学的重点关注点：

1. 这个功能的场景到底解决了什么问题。
2. 产品原型设计（可以提一下是 vibecoding 了一个 demo）
3. 上线后数据的回收与分析（最好写从数据中发现了什么 insights，并反哺到后面的功能优化）
4. 这个功能的成果，可靠的指标、数据来源、模型假设和结果边界。

## 怎么写才显得有产品 sense（核心方法论）

**判断标准只有一条：读完这条 bullet，招聘方能不能看出"这个决定换个人做可能就做错了"。**
看不出来，就说明写的是流程，不是判断。

### 1. 每条 bullet 必须含"判断"，不能只有"动作"

产品的稀缺性在**取舍**，不在执行。所以每条要能回答「**为什么这么做，而不是那样做**」。

| ❌ 只有动作（谁都能写） | ✅ 带判断（体现取舍） |
|---|---|
| 建立评测标准，测试并比较文本/生图/生视频模型 | 生图模型选型时放弃「单图质量最优」的候选，改用一致性更强的模型——漫剧的核心体验是跨分镜人物不跑形，单图再美也救不了断裂感 |
| 通过行业调研、客户调研分析行业痛点 | 调研后把目标用户从「网文作者」收窄到「中小漫剧工作室」：作者更在意剧情原创性、对 AI 出图容忍度低；工作室按件计酬，对「省 70% 分镜工时」的付费意愿明确 |
| 负责多环节 workflow 搭建与 prompt 迭代 | 把「剧本→分镜」拆成人设/场设/分镜三个独立节点而非一次生成：三者错误率不同，拆开后能单独定位失败环节，迭代周期从按天变成按小时 |

### 2. 按「洞察 → 决策 → 结果」组织思路，不要按「背景 → 过程 → 结果」

- **洞察**：你发现了别人没发现的什么？（数据异常、用户行为矛盾、竞品盲区）
- **决策**：基于这个洞察你做了什么取舍？放弃了什么？
- **结果**：数据 + 这个结果验证/推翻了什么假设

**这是思考框架，不是书写模板。** 下面示例为了讲清逻辑才标了「洞察/决策/结果」，实际落笔时：

- 不必逐条加这三个前缀词，也不必每个项目都用同一组标签
- 需要小标签时按该项目的实际逻辑自拟（如「问题本质」「判断信号」「方案取舍」「结果与代价」「能力边界」）
- 内容本身已经清晰的，直接写 bullet 更干净

```
（以下标签仅为讲解方便，实际写作时不必照抄）
✅ 洞察：POI 表态 90% 是「只打分不写字」，说明用户不是不想表达，是不想承担「写点什么」的成本
✅ 决策：不做「引导写字」（提高成本），改做「AI 抽好让你选」（降低成本）；同时保留节选面板，
        因为完全自动填充会让内容失真、伤害社区真实性——宁可牺牲一部分自动化率
✅ 结果：带图表态 +90%、优质表态 +110%，总量 -10%——证明「降成本」比「强引导」有效，
        且用户愿意为质量牺牲发布量
```

### 3. 主动写"负向结果"和"边界"，这是资深度信号

只报喜的简历一眼就是初级。敢写代价、失败、边界的人才像真做过事的。

```
✅ 表态总量 -10%，是预期内的代价：AI 填充抬高了内容门槛，一部分「随手打分」用户流失，
   但换来内容结构改善，判断这笔交换划算
✅ 该策略在美食/景点类目有效，购物类目提升不明显——SKU 类笔记的文字本身缺少可复用的表态素材
✅ 项目最终未上线，原因是 XX，从中总结出 YY
```

### 4. 数据要"带解释"，不要裸奔

裸数据没有说服力，要说清**为什么这个数字值得关注**。

| ❌ 数据裸奔 | ✅ 数据带解释 |
|---|---|
| CTR +50% | POI 一级页表态模块 CTR +50%——这个位置此前只外透星级，是全页信息密度最低的模块，改版后成为二级页最大流量入口 |
| 优质表态量 +110% | 优质表态量 +110%（口径：≥30 字且含图），这是社区内容供给的核心先行指标 |

### 5. 动词要精确到职责层级

| 动词 | 适用情形 |
|---|---|
| 定义 / 判断 / 收窄 / 取舍 | 你做了方向性决策 |
| 主导 / Owner | 你是唯一负责人，端到端负责 |
| 设计 / 拆解 / 搭建 | 你产出了具体方案或系统 |
| 推动 / 协同 | 你跨团队拿到了资源或对齐 |
| 参与 / 支持 | 你是执行者之一（诚实用这个，不要虚高） |

### 6. 一段实习最多 2-3 个项目，每个项目 3-4 条 bullet

宁可深不可全。把最能体现判断力的项目写透，其余一句话带过或删掉。
**招聘方看简历平均 30 秒，堆 8 条平庸 bullet 不如 3 条有洞察的。**

### 7. 禁止出现的"空话"清单

以下表述**必须替换掉**（它们不传递任何信息）：

- ❌「负责相关工作」「参与整体建设」「完成产品闭环」
- ❌「提升了用户体验」（怎么提升？什么指标？）
- ❌「深入分析」「有效沟通」「积极推动」（形容词不是证据）
- ❌「熟悉/了解 XX 方法论」（放技能栏，不要放经历里）
- ❌「与开发、设计紧密配合」（这是本职，不是亮点）

## 结合 JD 的定点润色

核心：经历是素材，JD 是镜头，润色是选镜头角度。不改写事实，不把 JD 的词硬塞进简历，而是把经历里与 JD 匹配的侧面加重、置前、强化措辞。

### JD 信号词 → 强调角度

| 职位 | JD 信号词 | 应强调的侧面 |
|---|---|---|
| 产品经理 | 需求分析、用户调研、产品规划、PRD、原型、迭代、上线 | 怎么定义问题、怎么设计方案、怎么推动上线、数据结果 |
| 数据分析 | SQL、指标、看板、AB 测试、归因、建模、洞察 | 怎么用数据做决策、分析发现了什么、怎么验证 |
| 商业分析 | 行业研究、竞品分析、市场规模、商业模型、战略、机会点、ROI | 怎么分析行业/竞品、怎么判断机会、商业价值 |
| AI 产品 | 大模型、LLM、Agent、Prompt、评测、RAG、效果优化、AI 应用 | 怎么衡量/提升 AI 效果、技术判断、评测体系 |
| 通用（所有职位） | 跨团队、推动、协调、Owner、结果导向 | 怎么协调资源、推动上线 |

### 边界规则

1. 只能调角度 / 权重 / 措辞，不能新增不存在的事实（呼应「证据规则」）
2. 与 JD 错开的侧面，跳过不强套；只强化能对的，绝不硬凑
3. 经历与 JD 完全没有匹配侧面时，从「学习能力 / 可迁移」角度补，并明确标注这是迁移而非已有经验

## 证据规则

将团队产出归属于团队。仅在用户的描述支持时，才使用 "主导（led）"" 负责（owned）""共同开发（co-developed）"" 支持（supported）"或" 贡献（contributed）"。

不得编造样本量、指标、软件实现、奖项、活动成果或上线状态。

区分实际业务成果与案例预测、模拟、课程作业和拟议策略。

将内部或机密数据保持在适当的抽象层级。标注为内部分析，而非暴露敏感细节。

当素材与用户最新澄清冲突时，以用户澄清为准，并仅在来源衍生的细微差别仍然有效时予以保留。

## 好的表述案例

**腾讯 · 产品实习生（WorkBuddy）· 2021/07**

**项目：PPT 场景评测体系与数据飞轮**

- 痛点：PPT 生成质量缺乏统一度量，问题难定位、优化难验证
- 评测体系：基于用户真实使用数据，按任务难度从浅到深构建约 50 个评测 case，制定打分标准，以定位模型在不同难度层级上的能力边界
- 数据闭环：搭建评测网站，评测结果持续回流，提炼高频失败 case 的共性问题，反哺模型与产品迭代

**项目：对话流式体验与结果展示组件**

- 主导整体流式对话体验设计，结果呈现方式直接影响用户对产出的采纳
- 设计 showwidget 组件，统一承载结果展示、模板选择等交互，为不同类型产出建立一致的交互范式
